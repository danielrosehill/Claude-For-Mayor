Record a municipal problem that arrived without a testimony behind it: noticed while reading existing material back, inferred from an account that was about something else, or simply raised in a working session. Follow the `municipal-policy-methodology` skill throughout, and read `observations/index.md` before writing — its rules bind this command.

Input: $ARGUMENTS — the problem, and any indication of where it came from.

## The one rule that makes this document class safe

An observation is admissible **only** because it declares its own provenance. Get that wrong and the whole class becomes a way to launder inference into evidence, which is the failure it exists to prevent.

So: **establish the lineage before writing anything else**, and do not guess at it. If you cannot say precisely how this problem came to be on file, ask the user. "It came up somehow" is not an origin.

## Steps

1. **Trace the lineage.** Work out which of these it is, and be honest when it is the third:
   - **In the existing material but never its subject** — the words are already on file in a testimony or a context document, mentioned in passing as texture around a different grievance. Strongest lineage available here. Quote or cite the document.
   - **Inferred from the material** — follows from something on file but nobody said it. Name the inference and name who made it.
   - **Neither** — it occurred to you or to the user, unprompted. Say so plainly. This is allowed and it is the weakest standing; an observation of this kind that also lacks a plausible municipal lever is usually not worth writing.

2. **Check it is not already covered.** Search `testimonies/`, `policy/*/index.md` and the other observations. If an existing policy area's tracker already carries it as a fact to establish, add it there instead and stop — a duplicate observation is worse than none.

3. **Apply the same redaction rules as testimony.** Full names of private individuals, exact addresses and identifying third-party details are removed or generalised. Inference does not relax this; if anything it tightens it, because an inference about a household can expose the household that gave the account without their having said the thing.

4. **Write the file** to `observations/YYYY-MM-DD-<slug>.md`:
   ```yaml
   ---
   title: <short title>
   description: <one line>
   date: YYYY-MM-DD
   origin: <a sentence, not a category — how this came to be on file, and what it is not>
   opens: <policy-area slug it would belong to, or `nothing yet`>
   status: observation — not promoted
   last-verified: YYYY-MM-DD
   ---
   ```

5. **Write the body**, in this order:
   - Restate the lineage in prose in the opening lines. Where it is weak, say so before the reader has to work it out. Where an inference is being made about a real person's circumstances, flag it explicitly.
   - The problem itself.
   - Where it touches material already on file, with file-relative links.
   - **Facts to establish** — a table, every row `[UNVERIFIED]`. Hypotheses about which class a lever would fall into are permitted here and must be labelled as hypotheses; the gate is not run by this command and nothing here is a finding.
   - **What would open it** — the specific testimony that would promote this. This is the most useful section in the document, because it converts a vague wish for more accounts into a concrete ask.

6. **Add a row to the index table** in `observations/index.md`, and an entry to the `Observations` sidebar group in `site/astro.config.mjs` — the sidebar is hand-written, not autogenerated.

7. **Do not open a policy area, and do not touch the planks array or the status tables.** Areas open on testimony. If the observation is strong enough that opening an area feels right, that is the signal to go and get the testimony, not to skip it.

8. **Consider whether the spine moved.** If the observation is an instance of a mechanism already named in `platform/spine.md`, add it there. If it contradicts one, say so on that page — a mechanism caught being wrong is the point of having written it down early.

## Restraint

Observations cost nothing to write, which is the danger: a list of every conceivable municipal shortcoming is a mood, not a platform. If `observations/` ever grows longer than `testimonies/`, the project has started generating its own evidence base. Say so rather than adding to it.
